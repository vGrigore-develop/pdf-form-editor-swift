Status as of 2026-10-10. This covers the automatable parts of S1, S5 and S7, run on synthetic fixtures because the real voucher template is not available yet. Nothing here was checked in Preview, Chrome, Acrobat or PDFKit.

## S1: writer, MuPDF side. PASS (automatable part)

`s1_fields.py` adds 3 text fields and 2 image fields to `synthetic_voucher.pdf` through the object API (`get_new_xref`, `update_object`, `xref_set_key`) and saves incrementally.

Checks that pass:
- **Byte prefix:** the original bytes are an exact prefix of the output.
- **libqpdf check:** clean.
- **MuPDF open:** no repair needed, and no `/NeedAppearances` was written.
- **MuPDF read-back:** exactly one widget per name, with the right types (Text ×3, Button ×2) and the expected rects.
- **Image fields:**
  - `/Ff 65536`, `/MK /TP 1` and `/MK /IF` are present;
  - `photo` carries `/A << /S /JavaScript /JS (event.target.buttonImportIcon\(\);) >>`;
  - `logo` (toggle off) has no JS.
- **pypdf:** `get_fields()` returns exactly the 5 names, the 5 widgets are in page `/Annots`, and every `/P` is page 1.
- **PDFium:** `FPDFPage_HasFormFieldAtPoint` reports a text field (6) or a push-button (1) at each field centre, and the stored placeholder appearance is drawn. MuPDF draws it too.

Findings:
1. **The incremental section holds 14 objects:**
   - the catalog (new `/AcroForm` key) and the page (`/Annots` key);
   - 12 new objects: the font, the AcroForm, 5 appearance streams and 5 fields.

   Each changed object is necessarily written out whole in the update section. "Key-level" holds in the sense that matters: only the intended keys change and every other key is carried over verbatim. Suggested spec wording for 7.7 step 2: "modify keys, never rebuild dictionaries from the model; changed objects are re-emitted with all other keys intact".
2. **pypdf warning in strict mode:** `PdfReader(strict=True)` logs "Xref table not zero-indexed" on MuPDF's incremental xref. The update's xref subsections start at object 1, which is legal (ISO 32000 7.5.6). Default (non-strict) pypdf is silent and reads correctly. S9's "no library warnings" criterion should say that pypdf runs with its defaults, or list this warning as known and harmless.
3. **Missing or direct `/AcroForm`:** the code creates `/AcroForm` as an indirect object when it is missing, and promotes a direct `/AcroForm` to an indirect one, so later edits stay key-level. `/DR /Font` entries and `/DA` are added only when they are missing.
4. **Font:** base-14 Helvetica (`/Helv`) was used. Noto Sans embedding and the encoding choice belong to S2.
5. **JS action placement:** the JS action is written as the widget's `/A` (mouse-up). Whether Acrobat's own image field uses `/A` or `/AA /U` must be confirmed in S4.

Not verified: editing the fields in Preview, Chrome and Acrobat Reader (the actual pass criterion), and the PDFKit control output. To check by hand, open `spikes/out/s1_fields.pdf` in the three viewers.

## S5: shape cut. PASS (automatable part: MuPDF + PDFium renders, re-edit, reversal, q/Q fallback, curve segment)

`s5_cut.py` runs six scenarios. Each of a-d is applied, then re-edited, then removed, and each step is a separate incremental save.

| | Input | Outline (apply → edit) | Mode |
|---|---|---|---|
| a | voucher | reference (11 lines + semicircle) → edited | Wrap |
| b | voucher | with a curve segment → reference | Wrap |
| c | voucher | reference → curve, XObject forced (10-stream concat path) | XObject |
| d | 1 stray Q | reference → edited | XObject (auto) |
| d2 | 2 stray Q | reference → edited | XObject (auto) |
| e1/e2 | 1 / 2 stray Q | Wrap forced, to show why the guard exists | - |
| f | voucher + S1 fields | reference | Wrap |

Method: a reference mask is computed independently of the PDF. Pixel centres are tested even-odd against the outline, with arcs sampled on the true circle. Each cut render is compared with that mask and with the unclipped original render.

All checks pass:
- **Outside is blank:** every pixel more than 1 px from the outline is pure white, in both MuPDF and PDFium.
- **Edges:** the 50 % coverage edge is within 1 px of the analytic outline, and MuPDF and PDFium are within 1 px of each other, at 150 DPI.
- **Interior:** flat areas are identical to the original render.
- **Re-edit:**
  - the outline reads back from `/PieceInfo`;
  - the new `cutStart` is used, and the old one is no longer referenced from `/Contents`;
  - the original streams stay wrapped in order.
- **Reversal:**
  - the `/Contents` value is restored exactly, whether it was a direct array or a single ref;
  - `/Resources` is restored exactly;
  - the original content stream objects are byte-identical, both the dictionary and the raw stream;
  - MuPDF and PDFium renders are **pixel-identical** to the original.
- **Incremental saves:** every save is an append (byte prefix of the previous one), and libqpdf is clean after apply and after remove.
- **Recovery without PieceInfo:** the marker comment finds the cut streams, and the outline rebuilt from the clip path is within 0.084 pt. That residual is the Bézier approximation of the arc.
- **f:** page `/Annots` is untouched by the cut, and MuPDF and pypdf still find all 5 fields.
- **q/Q tokenizer unit tests:** Q inside strings, comments and inline image data, `/Q` as a name, and unclosed q.

Findings:
1. **pypdfium2 render scale:** `page.render(scale=…)` picks an integer bitmap size and stretches the page to fill it. At 150 DPI that skews the scale by about 0.1 %, which is 0.8 px at the right edge of an 842 pt page. The skew alone made the "edges within 1 px" check fail. `common.render_pdfium` renders with an exact matrix (`FPDF_RenderPageBitmapWithMatrix`) into a MuPDF-sized bitmap. **Spec impact (section 9):** golden renders and the MuPDF-vs-PDFium comparison must use an exact-scale render, not pypdfium2's default.
2. **MuPDF clip compositing:**
   - Under a clip, MuPDF's anti-aliased artwork edges differ from the unclipped render by up to 5-6/255 (about 5,800 px on this page). Flat areas are identical.
   - PDFium shows no difference at all.

   So "pixel-identical" holds only for the reversal comparison, not for interior-under-clip. The test plan's 1 % golden tolerance is fine.
3. **One stray `Q` does not break Wrap** (e1): the inner `q` absorbs it and the clip survives. Two stray `Q` leak, with 218,102 px painted outside (e2). The guard is still right: an unbalanced original also loses its graphics-state isolation, and `cutEnd` then pops the wrong level.
   - The code treats min depth < 0 **or** final depth ≠ 0 as unbalanced, and takes the XObject route for both.
   - For final depth > 0 (an unclosed `q`), a cheaper alternative would be extra `Q`s in `cutEnd`. Not needed.
4. **Store `/OrigContents` in Wrap mode too.** Restoring `/Contents` from the array minus its first and last entries turns a single-ref `/Contents` into a one-element array, and loses an indirect array object. Storing the exact original value makes reversal exact in every case. **Spec change for 5.4:** `/OrigContents` always; `/Remove` restores it.
5. **XObject mode needs two more keys,** missing from the 5.4 key list. The implementation:
   - replaces the page `/Resources` with a new `<< /XObject << /VEOrig form >> >>`;
   - moves the original (or inherited) resources into the form's `/Resources`, so shared resource dictionaries are never modified.

   Reversal therefore needs `/OrigResources` and `/XObjectRef`. **Spec change for 5.4:** add `/OrigResources` (or null when the page inherited its resources) and `/XObjectRef`.
6. **"Original streams referenced as the XObject's data where possible" is not possible.** A Form XObject needs its own stream dictionary (`/Type /XObject /Subtype /Form /BBox`), and editing the original stream's dictionary would modify the original object. So the form is always a copy:
   - for a single-stream original, the raw encoded bytes are copied with the same `/Filter` and `/DecodeParms` (no re-encode);
   - for several streams, they are concatenated and re-compressed.

   **Spec wording:** "a copy of the original content (raw bytes when there is one stream); the original objects stay untouched".
7. **`/LastModified` on the page:** ISO 32000 requires page `/LastModified` whenever `/PieceInfo` is present. The code sets it. **Add to 5.4.**
8. **Removal leaves traces:** after removal the page keeps `/PieceInfo /VoucherEditor << /LastModified … /Private <<>> >>` and `/LastModified`. The criteria (content streams byte-identical, render identical) are met, but the page dictionary is not byte-for-byte the original. If that matters, store whether `/PieceInfo` existed before, and delete the whole entry on removal.
9. **PyMuPDF null quirk:** `xref_set_key(x, "A/B/Cut", "null")` on a *nested* path stores `/Cut null` instead of deleting the key. On a top-level key it deletes. The workaround rewrites the app's own `/Private` dictionary. The C shim should use `pdf_dict_del`.
10. **Arc to Bézier at 90 degrees or less:** the measured maximum radial error is 2.73e-4 × r, which confirms the spec's "under 0.03 %". At r = 247.5 pt that is 0.067 pt (0.14 px at 150 DPI), irrelevant for the clip. A 60-degree split gives 2.4e-5 × r and a 45-degree split gives 4.2e-6 × r.
11. **Re-edit garbage:** each re-edit leaves the previous `cutStart` in the file as an unreferenced object. This is expected with append saves, and "Save As Compacted" removes it.

Not verified:
- part 1 in Preview, Chrome and Acrobat, and Print to PDF from Preview (outputs to open by hand: `spikes/out/s5*_1_cut.pdf`, `s5*_2_edit.pdf`, `s5f_fields_and_cut.pdf`);
- the cover annotation (v1, not built);
- the real template.

## S7: SVG import geometry. PASS for the inputs available (no real editor exports)

`svg_import.py`:
- **Path parser:** all of M L H V C S Q T A Z, absolute and relative, including packed arc flags, `.5.5` and exponents.
- **Shapes:** rect (rx/ry), circle, ellipse, polygon, polyline.
- **Groups and transforms:** nested `g`; matrix, translate, scale, rotate with a centre, skewX and skewY.
- **Units and viewBox:** `viewBox`, `width`/`height` in px, pt, pc, mm, cm or in, and `preserveAspectRatio`.
- **Arcs:** an arc stays an arc when rx = ry and the accumulated transform is a similarity; otherwise it becomes cubics of 90 degrees or less.
- **Shape choice and placement:** the largest closed subpath wins; open subpaths are noted and ignored. Placement is Fit to page or Actual size, with the y-flip.

`fitting.py` implements 5.6.3 steps 1, 2, 3, 5 and arc re-projection; step 4 (merging curves) is not done yet.

The tolerance is 0.1 pt for all checks below.

| Input | Result |
|---|---|
| `handwritten.svg`: 9 nested groups using every transform type, relative commands, an `A` arc under a flipping chain, a decoy rect, an open polyline | 11 L + 1 A, vertices within 1e-13 pt of the reference, arc centre and direction correct, decoy loses the area vote, open path noted. Actual size (297 x 210 mm artboard, viewBox 1684 x 1190, meet) correct to 2e-13 pt. Fitting is a no-op. |
| `primitives.svg`: 10 elements | Expected kinds for each: rounded rect 4L+4A; elliptic corners 4L+4C; circle 2A; ellipse 4C; rotated rounded rect keeps 4A; non-uniformly scaled circle 4C; packed-flag path 3L+1A. Corner arc centres exact. |
| `cubic_only.svg`: everything as cubics, a split line, semicircle as 3 × 60° cubics, 0.04 pt jitter | Before fitting 5L + 10C; **after "Detect lines and arcs": 11 L + 1 A**, vertices within 0.010 pt, outline within 0.050 pt, steps exactly orthogonal, arc centre within 0.005 pt |
| `nonuniform.svg`: scale(1.2, 1) | The arc imports as curves (11 L + 2 C), and fitting does not turn the half ellipse into a circle |
| Oracle | svgelements stands in for nanosvg (a C library, not set up). Agreement is 1e-10 to 0.02 pt on every element, and 0.079 pt on the non-uniform half ellipse (see finding 2). |

Findings:
1. **Fit to page with a slightly different aspect ratio:** the spec says the viewBox "maps onto the page MediaBox". Mapping exactly with separate x and y scales would be a non-uniform transform, and would turn every arc into curves even at a 0.1 % aspect mismatch. The implementation uses a uniform scale, centred ("meet"), whenever the ratios differ within the 1 % window. **Spec wording for 5.5:** "maps uniformly and centred".
2. **Imported elliptical arcs:** an arc converted to cubics of 90 degrees or less has an error of 2.7e-4 × r. That is 0.079 pt for the non-uniform test, close to the S7 limit, and arcs with a radius above about 370 pt would exceed 0.1 pt. **Recommendation:** split imported elliptical arcs at 45 degrees or less (error 4.2e-6 × r). Clip paths can stay at 90 degrees.
3. **SVG fitting tolerance:** the spec defines the tolerance only for PNG (default 0.5 pt). With 0.5 pt, snapping may move SVG points beyond S7's own 0.1 pt criterion. **Recommendation:** a default fitting tolerance of 0.1 pt for SVG imports.
4. **Segment count:** the synthetic shape has a symmetric notch with 4 jogs, so its target is 11 lines + 1 arc, not the spec's "about 8 + 1" for the real shape. Rerun with the real outline when it exists.
5. **Not implemented yet:**
   - curve merging (step 4);
   - percentage lengths;
   - `preserveAspectRatio` for Fit to page (it is always meet/centred; it is honoured for Actual size);
   - CSS/`style` geometry, `<use>` and `clipPath`, which are reported as notes per the spec.

Not covered: real exports from Illustrator, Figma, Inkscape and Affinity; nanosvg itself.

## S3: preservation. PASS (automatable part), with one finding on approval signatures

`s3_preservation.py` builds three fixtures in `Tests/Fixtures/` and adds the S1 fields (3 text, 2 image) to each through the S1 path (key-level object edits, incremental save):
- `js_form.pdf`: the synthetic voucher plus document-level JS (`/Names /JavaScript`, one string-valued and one stream-valued), a text field with keystroke/format/validate actions (`/AA /K /F /V`), a calculated field with a stream-valued `/AA /C` and `/AcroForm /CO`, and a push-button with a mouse-up JS action. 8 `/JS` values in all. Built with pikepdf, because there is no Acrobat Pro here.
- `signed_approval.pdf`: one approval signature (pyHanko, self-signed RSA-2048 key generated into `spikes/out/s3_keys/`).
- `signed_certified.pdf`: one certification signature, DocMDP P=2 (fill forms).

Checks that pass:
- **JS:** all 8 original `/JS` values are byte-identical after the save (compared as raw decoded bytes, stream-valued ones included). The only new JS is the image field's `buttonImportIcon`.
- **Existing form:** the existing `/AcroForm` is reused (the 3 old fields are kept, the 5 new ones are added), `/CO` is untouched, and the `/Names /JavaScript` tree is still there.
- **Bytes:** the original is an exact prefix in all three cases, and libqpdf is clean.
- **Signatures:** pyHanko reports both signatures as cryptographically intact and valid, with coverage ENTIRE_REVISION, after the fields were added.

Findings:
1. **pyHanko's diff policy rejects new fields after an approval signature.** Its verdict is `modification_level=OTHER`, `docmdp_ok=False`, `bottom_line=False`, and it logs "More form fields added than expected". So "the approval signature verifies in pyHanko" holds for the signed bytes, but pyHanko's overall verdict on the document is negative. The certification signature (P=2) gives the same verdict, as expected. **Spec impact (7.7, Signatures):** warn on *any* signature, not only certification, that adding fields will show as a disallowed change in strict validators, even though the signed revision stays intact. Acrobat's view is still unverified.
2. The fixture JS form is synthetic. Rerun with a real Acrobat-made form when one exists.

Not verified: Acrobat's view of either signature; whether the JS still runs in Acrobat.

## S9: programmatic fill. PASS (automatable part, all three libraries)

`s9_fill.py` fills `spikes/out/s5f_fields_and_cut.pdf` (the S1 fields plus the S5 cut on page 1) with PyMuPDF, pypdf (defaults, non-strict) and pdf-lib 1.17.1 (`spikes/node/`, local `npm install`, nothing global). Each library writes an unflattened and a flattened output. Images go in with pdf-lib `getButton().setImage()`, PyMuPDF `insert_image` at the widget rect, and pypdf by merging an overlay page that draws the image at the rect.

Checks that pass, 104 in all:
- **Fields:** every library finds all 5 fields by name, with exactly one widget each, on page 1, and the expected rect within 0.01 pt.
- **No errors:** none in any library. pdf-lib prints no warnings.
- **Text placement:** the ASCII text extracts exactly and every word lies inside its field rect, in all 6 outputs.
- **Images:** green image ink covers more than 30 % of each image slot, in MuPDF and PDFium renders.
- **Clip intact:** in all 6 outputs plus the 2 pdf-lib Noto outputs, no pixel more than 1 px outside the outline is painted, in either MuPDF or PDFium (rendered with annotations and forms). The cut's closing `Q Q` behaves as 5.3 predicts: content appended by `insert_image`, `merge_page` and flattening is not clipped, but it is also not broken.

Findings:
1. **The placeholder hides images drawn as page content.** PyMuPDF `insert_image` and pypdf's merged overlay draw into the page content, which sits below annotations. If the image widget stays, its opaque placeholder appearance covers the image: 0 % of the image is visible. Fillers that draw at the rect must therefore delete the image widget, or flatten after replacing its appearance. pdf-lib `setImage` is not affected, because it replaces the widget appearance. **Spec impact (6.1 and the field map notes):** document the "draw, then delete the widget" recipe for PyMuPDF and pypdf. Alternatively, consider a placeholder without an opaque background (a border and label only); that would need a check in S4 that Acrobat still shows it as a slot.
2. **A pypdf warning comes from the cut's `/PieceInfo` refs.** `PdfWriter(clone_from=reader)` logs "Object count 42 exceeds defined trailer size 33" on any file with a cut, including a qpdf-rewritten copy, and is silent once `/PieceInfo` is removed. The template's trailer `/Size` is correct; pypdf clones the original content streams referenced from `/OrigContents` a second time. Reading alone (`PdfReader`) is silent. The output is correct, only larger. The check treats this one message as known; no other pypdf warnings appear. Possible mitigation if it matters: keep the refs (needed so rewriting tools renumber them correctly) and accept the warning, or record that S9's "no warnings" excludes it.

**Basic S2 (diacritics), using `Tests/Fixtures/NotoSans-Regular.ttf`:** the font was copied from a local LibreOffice bundle; it is OFL and has all of ă â î ș ț and their capitals.
- **pdf-lib with a code-supplied Noto Sans** (`updateFieldAppearances(font)`): "Țară Ștefan ăâî ĂÂÎ șț ȘȚ" extracts exactly, inside the rect, both unflattened and flattened. PASS.
- **pdf-lib with only the template's `/Helv`:** throws `WinAnsi cannot encode "Ț"`. The filling code must supply a font, as 7.6 expects.
- **PyMuPDF `widget.update()` with the template font:** the output is garbled (`'Ț ă Ș f ăâî ĂÂÎ ȘȚ'`, partly outside the rect). PyMuPDF only uses its built-in fonts for widgets.
- **PyMuPDF with a code-supplied Noto Sans,** drawn with `insert_textbox` at the widget rect after deleting the widget: exact. PASS.
- **pypdf's appearance generation with `/Helv`:** characters outside WinAnsi become `?`. pypdf relies on the `/DR` font, so with the planned embedded Noto Sans in encoding A this is the case S2 must settle.

So, with the S1 base-14 font, only code-supplied fonts work. That is consistent with the spec, and S2's encoding A/B comparison with an embedded Noto Sans in `/DR` is still to do.

## S10: crop form fields to the cut outline. A + C chosen (appearance clip plus cover annotation)

Question (SPEC 5.3): the cut clips page content only. Widgets are annotations drawn on top, and content a filler appends after the cut's end stream is outside the clip, so a field that crosses the outline shows outside the shape. The real template used during development (private, not in the repo) has exactly that: its main image field (`/Rect [0 75.27 365.23 528.22]`) sticks out past the stepped left edge (x 31.35 to 141.30) of the smart-outline result (11 lines, 3 arcs).

`s10_crop.py` builds each candidate on a copy of that template, fills it with the S9 fillers (PyMuPDF: `widget.update`, `insert_image` at the rect and delete the image widget, `bake`; pypdf: field values, overlay page `merge_page`, `flatten=True`; pdf-lib: `setText`, `setImage`, `form.flatten`), and counts pixels more than 1 px outside the outline that are not white, rendered with MuPDF (annots), PDFium (`FPDF_ANNOT` + `FFLDraw`) and PDFKit (`pdfkit_render.swift`, the engine of macOS Preview). The filled image covers about 35,000 px outside the outline at 150 dpi when nothing is done.

What the page outside the outline actually is: after the cut it is blank page, which every viewer shows as white. The template's artwork is inside the outline. So a white cover is visually the same as the blank page there.

Pixels painted outside the outline (MuPDF / PDFium / PDFKit; 0 = cropped):

| Variant | unfilled | PyMuPDF unflat / flat | pypdf unflat / flat | pdf-lib unflat | pdf-lib flat |
|---|---|---|---|---|---|
| base (cut only) | 4570 / 5980 / 4748 | 35k everywhere | 35k everywhere | 35k / 35k / 35k | 35k everywhere |
| A: clip each crossing widget's /AP to the outline | 0 / 0 / 0 | 35k everywhere | 35k everywhere | 35k / 35k / 35k | 35k everywhere |
| B: leave the clip open (cutEnd without `Q Q`) | 4570 / 5980 / 4748 | 35k everywhere | 0 | 35k / 35k / 35k | 0 |
| C: cover annotation (/Watermark, last in /Annots) | 4570 / 5980 / 0 | 0 | 0 | 35k / 35k / 0 | 0 |
| A + C | 0 | 0 | 0 | 35k / 35k / 0 | 0 |

Findings:
1. **A works in all three engines for the template as saved.** The wrapper form keeps the original appearance's space (identity /Matrix, the transformed /BBox), so the bbox-to-/Rect mapping is unchanged, and the original stream is invoked unchanged under the clip. It does nothing for filler output: pdf-lib `setImage`/`setText` and pypdf replace /AP /N, and PyMuPDF/pypdf draw the image into the page content.
2. **B is rejected.** PyMuPDF rebalances the page before drawing (`Page.wrap_contents` counts the missing `Q`s with `pdf_count_q_balance` and appends them), which closes the clip before `insert_image`. pypdf (`merge_page` wraps the old content in `q ... Q`) and pdf-lib (`normalize` wraps it in `q ... Q`) happen to keep it, because their single `Q` pops the inner `q` only. It never reaches widgets, and it breaks ISO 32000 8.4.2 (q/Q balanced over the page's content streams), which is what the S5 guard protects. No balanced construct carries a clip past the end of the page content (/Group does not clip, and there is no annotation-level clip).
3. **C covers everything that ends up in page content, in all three engines,** including the flattened outputs (PyMuPDF `bake` bakes the cover too, last, so it stays on top; pdf-lib and pypdf flatten only fields and leave the cover). **But MuPDF and PDFium draw widgets after all other annotations,** so the cover is below every widget there; PDFKit draws in /Annots order and covers them too. This answers the S5 cover question: the cover is not drawn above widgets in MuPDF or PDFium (so not in Chrome).
4. **A + C leaves one gap: an appearance a filler rebuilds without flattening** (pdf-lib `setImage`, unflattened) still shows outside in MuPDF and PDFium.
